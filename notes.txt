-----------------------------------------------------------
Sketch DSL
-----------------------------------------------------------


--- GOAL ---
a domain specific language for art which can be compiled to
gcode for the uunatek to draw. ideally this allows language
models to efficiently describe images instead of just directly
generating gcode. this hopefully will help the llms to build
abstractions about the art, which after compilation can be 
expanded into immense gcode, similar to how high level cs
languages can express complex ideas with minimal code and be
expanded into asm or bytecode.

the language must be similar enough to english and popular 
programming languages to take advantage of what they were 
trained on.

for example we could describe a curve, compiled to bezier curve,
as "some_curve : sketch = curve from p0 to p1 through p3 and p4"
sketches can be sent to the "draw" command which adds the lines
to canvas "draw some_curve". when a program is finished running
the canvas is then path optimized and translated into g-code.

--- IDEAS --
we need to have an easy way to describe primitives, transformations
and identifiers.

**types**
	- number : float
	- vec : (x, y) : float * float
	- sketch : primitive | transformed sketch | list of sketch 


**primitives**
	- dot : vec ---> compiled this to a small circle
	- hdash : vec --> compiled this to very short horizontal line
	- vdash : vec --> compiled this to very short verticle line

	- line : (p0, p1) : vec * vec
	- curve : (p0, through, p1) : vec * list vec * vec
		--> this is like a quadratic bezier curve
	- arc : (center, radius, a0, a1) : vec * vec * float * float
		--> this can be an oval, circle, somewhere in between depending on radius
		    and angle0 / angle1

**functions**
	- scaling
	- rotations
	- re-positioning: relative to statement "S relative to p0" with p0 a point
	- repetitions: 
	- symmetries
	- bounding --> compile time bounds to verify

functions take **types** as inputs. they can be partially applied like how
Ocaml allows for partial application of functions and can be given names.

if we can build modularization into the language that would be
very helpful too. for example if the language allows an identifier
to capture an expression, say were building a image of a person and
we say

"face : sketch = symmetric along y_axis half_face"
then "face" becomes an identifier that can later be rotated, translated,
scaled, or applied in many places, because it is evaluated as a sketch.

this would allow claude to divide and conquer the painting. it would
need to account for how the parts at lower levels interact when brought
together, for example, if a "face" was combined with "sunglasses"
although maybe thats not the right way to think of it.

--- EXACTNESS ---
I thought a bit more about how an artist can form an sketch
and there are varying levels of exactness they apply to each
stroke. For example they may be very light and quick and not
so exact with their strokes in the beginning, but come back
and be more exact and less quick when they are adding detail.
there should be a way to express this easily, so many strokes
can be grouped together in a "draw" statement, but maybe we
require that the exactness or intent be specified as well.
i'll need to come up with the correct words to describe the
parameters of the different levels of exactness... but under
the hood it is pretty simple, that the positions can have
noise applied to them, and the gcode can specify faster or
slower motor speeds.

--- DRAFTING ---
an artist probably does not one shot all their paintings, and
they probably do many drafts before presenting their final
version. this maybe something that can be worked into the language
will more likely end up as a system, aside from the language.
a controlled loop where the LLM can have drafts (image + code)
and can iterate on their current draft with an adversary who
critiques that draft.

--- REFINE THE LANGUAGE ---
lets have three sketch primitives, namely dots, dashes, and strokes.
sketches are simply compositions of these primitives. we must also
sketches are really an array of primitives, or an array of sketches,
or an empty array. the language allows for vec and arithmetic such
as adding and subtracting and scaling. we can infer points from a
stroke, say we want a point on a stroke. since we have a start and
end point and a way to calculate that point during compilation.

--- LEVEL OF DETAIL ---
llms should express intention from a birds eye view and express
precision on small areas of work. it should allow information to
be passed down to workers at small levels, but at the same time
bring information back up the tree to orchestration. we need to
make abstractions avaiable, ways to extract information about a
sketch that is meaningfull, something like meta information. a
couple examples: center of mass calculation, convex to concave
shape decomposition; spatial positioning; field lines / flow
direction at any given point in a sketch;

--- OPTIMIZE GCODE ---
when we introduce the stroke type, we should compile it optimally.
we can take advantage of gcodes ability to represent arcs and cubic
splines.

--- USAGE CONTEXT ---
the language will be used by LLMs from within a iterative drawing
and drafting environment. the LLMs actually using it will be given
instructions by an orchestration agent. it is important to know
this because it will help shape the language itself. the LLMs using
the language can be considered the hand of the artist. the artist
consists of three entities: hand manager, a planner, and a dreamer.
the hand speaks Sketchlang and carries out the intentions of the
manager, likely with imperfections. The hand manager focuses on
following the planners steps, and provides detail to each part. the
planner envisions the painting as in its complete state, and provides
best estimated steps to get there and is injected with randomness
from the dreamer, maybe we can inject dreams of the artist we chose
as the personality. this all happens within a single iteration.
there will be multiple iterations and at the end, a critque will be
made, the planner must respond to those critiques. the language does
not need to know about that, but it should be built in a way that is
most helpful in that context.

--- REMOVING SYMMETRIES & SIMPLIFYING LANGUAGE ---
we should simplify the language and get the drafting system working.
the reflection and rotational symmetries sound nice but are likely
to complex at this point. ill consider adding them back eventually.
additionally, translation symmetry is being removed. same deal.

--- UPDATES ---
First we simplified the "hdash" and "vdash" into a singular "dash"
sketch.this sketch takes on a minimal size, same as before, however
now the direction is determined by the directions of the other sketches
on the canvas. each stroke produces a flow field in its direction p0
via p1, and those flow fields can be determined at any given point. we
default to horizontal if no strokes are in the sketch. Second we are
adding a new type, "stroke" which combines line and curve depending
on the number of control points. the "stroke" should be decomposed into
cubic splines and ideally make use of the G code: 
G5 Cubic Spline G5 X- Y- <I- J-> P- Q-
if that doesn't make sense than maybe we use something like Catmul Rom
spline. Third we want to apply noise to sketches as they enter into the
rendering function. for example we add "via" points to strokes, some
epsilon away from their path along the way. we also can slightly
translate (add or sub) the vecs in the sketch "scribble" has the most
noise applied "draw" gets some noise applied "trace" has no noise applied

--- INCREMENTAL IMPROVEMENTS ---
after using the language for a week with llms it has become
obvious that the language lacks some efficiency. we need many
tokens to describe similar structures, even if they are just
translations, rotations, and scaling of others. to make many
dashes we need to say exactly where each dash should go. to
draw many lines we need to duplicate those points and offset them.
there should be an easy way to make those symmetric
transfomrations { scale, move, rotate, mirror } and a way to
describe many strokes or dashes over an area, and a way to
describe line thickness.
these are all potential future improvements. the most usefull
are the symmetric transformations. lets address those first.

--- SYMMETRIC TRANSFORMATIONS ---
first lets consider the mirror syntax. we can take any sketch,
find its center, then move that to origin, call that normalized.
we can than mirror that normalized sketch about some axis defined
by a vec2, [1, 0] for x_axis [0, 1] for y_axis and anything.
after mirroring we can then translate the position back to the
original pre-normalized. 
(open question: should we consider that
the center of the mirrored will be different than the original?
-> not now )
let k : sketch = stroke from a to b via [c, d, e]
let k_about_y = mirror k about y_axis

--- SHADING ---
currently shading is difficult to describe succinctly. we need
lots of tokens for each dash. instead we should describe an area
about which to shade, then fill in that with some random dashes
an idea is that applying shade can be applied multiple times to
get more shade in areas.
the best move here is to introduce a "region" type that defines
a closed area. we can use this in a "shade" expression that is
evaluated to a sketch expression?

--- MIRROR ---
this function is now basically implmented. while implementing
it pointed out the complexity introduced by the "flow at <vec>"
statement that evaluates to a vec. the evaluate_sketch_basic
function does not resolve the value of a "flow at" and will
cause issues with the mirror if we use that as an axis to mirror
about. i.e "mirror <sketch> about flow at <vec>" will always
mirror about [1,0] because that is how we default this value.
therefore we should remove that expression. additionaly im
adding "scale" and "translate" "by" expressions.

--- COLLECT FLOW ---
this function needs to be addressed. it is not collecting
the evaluated splines, afaict. maybe we should instead
collect flows for a "primitive intermediate representation"
one thats only made of elements contributing to flow and
can not affect flow, this is reason for removing "flow at"
vector expression, because if that were allowed we could
define sketches that both affect the flow field and need
it to be created. the work around there could be just eval
the flow fields at the time of sketch, honestly optimal
solution.
