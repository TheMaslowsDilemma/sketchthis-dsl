Sketch DSL
-----------------------------------------------------------

--- goal ---
a domain specific language for art which can be compiled to
gcode for the uunatek to draw. ideally this allows language
models to efficiently describe images instead of just directly
generating gcode. this hopefully will help the llms to build
abstractions about the art, which after compilation can be 
expanded into immense gcode, similar to how high level cs
languages can express complex ideas with minimal code and be
expanded into asm or bytecode.

the language must be similar enough to english and popular 
programming languages to take advantage of what they were 
trained on.

for example we could describe a curve, compiled to bezier curve,
as "some_curve : sketch = curve from p0 to p1 through p3 and p4"
sketches can be sent to the "draw" command which adds the lines
to canvas "draw some_curve". when a program is finished running
the canvas is then path optimized and translated into g-code.

--- Language Ideas --
we need to have an easy way to describe primitives, transformations
and identifiers.

**types**
	- number : float
	- vec2 : (x, y) : float * float
	- sketch : primitive | transformed sketch | list of sketch 


**primitives**
	- dot : vec2 ---> compiled this to a small circle
	- hdash : vec2 --> compiled this to very short horizontal line
	- vdash : vec2 --> compiled this to very short verticle line

	- line : (p0, p1) : vec2 * vec2
	- curve : (p0, through, p1) : vec2 * list vec2 * vec2
		--> this is like a quadratic bezier curve
	- arc : (center, radius, a0, a1) : vec2 * vec2 * float * float
		--> this can be an oval, circle, somewhere in between depending on radius
		    and angle0 / angle1

**functions**
	- scaling
	- rotations
	- re-positioning: relative to statement "S relative to p0" with p0 a point
	- repetitions: 
	- symmetries
	- bounding --> compile time bounds to verify

functions take **types** as inputs. they can be partially applied like how
Ocaml allows for partial application of functions and can be given names.

if we can build modularization into the language that would be
very helpful too. for example if the language allows an identifier
to capture an expression, say were building a image of a person and
we say

"face : sketch = symmetric along y_axis half_face"
then "face" becomes an identifier that can later be rotated, translated,
scaled, or applied in many places, because it is evaluated as a sketch.

this would allow claude to divide and conquer the painting. it would
need to account for how the parts at lower levels interact when brought
together, for example, if a "face" was combined with "sunglasses"
although maybe thats not the right way to think of it.

--- examples of expressions ---

"relative to center of D curve from A to B through C"
	- this shows the "center of <expr>" expression which itself
	  is evaluated to a <vec2>.
    - "relative to" then shifts the expression after it to be
       shifted in scope. "relative to <vec2> <expr>"
"point A inside B"
	- this would create a compilation error if B exceeds Bs
	bounding box. Otherwise, would be evaluated to A.
	QUESTION: all <expr> can have a bounding box? -- yes
	able to create a bounding box?

"repeat A along C 10 times"
    - A is an <expr> and C is an <line | vector>

"scale A by 2.5 along C"
	- A is an <expr> C is a <vector>

-- exactness in drawing --
I thought a bit more about how an artist can form an sketch
and there are varying levels of exactness they apply to each
stroke. For example they may be very light and quick and not
so exact with their strokes in the beginning, but come back
and be more exact and less quick when they are adding detail.
there should be a way to express this easily, so many strokes
can be grouped together in a "draw" statement, but maybe we
require that the exactness or intent be specified as well.
i'll need to come up with the correct words to describe the
parameters of the different levels of exactness... but under
the hood it is pretty simple, that the positions can have
noise applied to them, and the gcode can specify faster or
slower motor speeds.

-- drafting --
an artist probably does not one shot all their paintings, and
they probably do many drafts before presenting their final
version. this maybe something that can be worked into the language
will more likely end up as a system, aside from the language.
a controlled loop where the LLM can have drafts (image + code)
and can iterate on their current draft with an adversary who
critiques that draft.

-- refine the language --
lets have three sketch primitives, namely dots, dashes, and strokes.
sketches are simply compositions of these primitives. we must also
sketches are really an array of primitives, or an array of sketches,
or an empty array. the language allows for vec2 and arithmetic such
as adding and subtracting and scaling. we can infer points from a
stroke, say we want a point on a stroke. since we have a start and
end point and a way to calculate that point during compilation.

-- level of detail --
llms should express intention from a birds eye view and express
precision on small areas of work. it should allow information to
be passed down to workers at small levels, but at the same time
bring information back up the tree to orchestration. we need to
make abstractions avaiable, ways to extract information about a
sketch that is meaningfull, something like meta information. a
couple examples: center of mass calculation, convex to concave
shape decomposition; spatial positioning.

-- optimizing gcode --
when we introduce the stroke type, we should compile it optimally.
we can take advantage of gcodes ability to accept arcs and cubic
splines!
